01

Aim

To study SQL injection as a consequence of mixing untrusted input with SQL syntax, and to demonstrate the prevention technique of parameterized queries in a local Flask and SQLite application.

02

Problem statement

Applications that build database statements by concatenating request values may let user input alter query meaning. This experiment executes that unsafe pattern only in an isolated, disposable SQLite database containing fictional records, then compares it with a parameterized training check. Training results never create an application session.

03

Theory

SQL injection is a code/data boundary failure. If application text is interpolated into a SQL statement, SQL metacharacters can be interpreted as part of the statement. An ordinary invalid login, by contrast, is simply a username or password that does not match a valid account; it does not change the query structure.

Parameterized queries use placeholders and bind values separately. SQLite parses the fixed statement and compares a bound username value; input is not parsed as SQL grammar. Here, authentication then independently checks a salted password hash.

Parameterized queries address SQL injection at the query boundary. They do not by themselves provide authorization, CSRF protection, secure deployment configuration, output encoding, rate limiting, or correct session policy.

04

Software requirements

  • Windows 10/11 with PowerShell or Command Prompt
  • Python 3.10 or newer
  • Flask 3.0.3 (installed from requirements.txt)
  • SQLite via Python's standard library
  • Current Chrome, Edge, or Firefox browser
05

Procedure

  1. Create and activate a Python virtual environment.
  2. Install the single Flask dependency from requirements.txt.
  3. Run python app.py; both local databases initialize automatically.
  4. Open http://127.0.0.1:5000.
  5. On Vulnerable Test, compare the fictional normal login with crafted text and observe the isolated query result.
  6. Submit the same values to Secure Authentication and observe that they are bound as data and rejected.
  7. Use Secure Test separately to verify the existing session dashboard and sign out.

Training account: trainee / TrainingPass123!. Existing application account: student / LabPass123!.

06

Implementation details

  • Flask serves overview, documentation, a comparison lab, and the existing secure login.
  • training_lab.db is reset on each start and contains only fictional accounts.
  • The vulnerable training check concatenates input and executes only a SELECT against that database.
  • The secure training and application login checks use bound queries and password-hash verification.
  • Only the existing Secure Test writes the Flask session used by the dashboard.
  • Generic database errors are shown to users while technical details remain in server logs.
  • The development server binds to 127.0.0.1 and runs with debug mode disabled.

08

Result and conclusion

The experiment demonstrates that parameterized SQL preserves the distinction between command structure and submitted values. The vulnerable outcome is confined to a resettable database of fictional records and never grants a dashboard session. Parameter binding is essential, but it is one part of a complete application security program.

09

Precautions

  • Run only on the local machine; do not expose this educational app to a public network.
  • Do not enable Flask debug mode or publish development secrets.
  • Use parameterized queries for all user-controlled database values.
  • Never copy unsafe query-building patterns into production code.
  • Use the sample credentials only for this local demonstration.
10

Viva questions and answers

1. What is SQL injection?

A vulnerability in which untrusted input changes the meaning of a SQL statement.

2. What causes SQL injection?

Mixing SQL syntax and untrusted values, commonly through string concatenation.

3. What is a parameterized query?

A fixed SQL statement with placeholders whose values are bound separately by the database driver.

4. Why does parameter binding prevent SQL injection?

Bound values are treated as data and are not parsed as part of the SQL grammar.

5. Is an invalid login an SQL injection?

No. It is a failed credential check; injection requires changing query interpretation.

6. What is a password hash?

A one-way derived representation used to verify a password without storing its plaintext value.

7. Why is input validation not enough?

Validation can constrain expected values but cannot safely replace separating data from SQL syntax.

8. Does parameterization fix every web security issue?

No. It addresses SQL injection, not authorization, XSS, CSRF, session flaws, or other risks.

9. What database is used here?

SQLite, accessed through Python's standard-library sqlite3 module.

10. Why is the vulnerable page simulated?

To explain the unsafe design without shipping an executable authentication-bypass endpoint.
